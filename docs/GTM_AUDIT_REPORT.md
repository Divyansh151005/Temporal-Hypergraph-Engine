# GTM Audit Report: Temporal Hypergraph Engine v1.0.1

_Audit date: 2026-11-10. Audited at `main` = `09f48ae` ("docs: add Show HN launch post"), tag `v1.0.1`._

**Verdict: NO-GO.** The engine, benchmarks and CI are launch-quality, and most of the narrative matches the code. Three issues would break the Hacker News launch in the first few minutes: the GitHub repository is private, the Python packages the README tells users to import are not on PyPI, and the vLLM integration is described more strongly than the code supports. All three can be fixed without new engine code. See [section 3](#3-actionable-launch-blockers).

## How this audit was done

Sources reconciled: `docs/01` to `docs/07`, `docs/MyUnderstanding/*` (mainly `GTM.txt`, `Integration.txt`, `Details.txt`, `Overview.txt`), `docs/LAUNCH_POST.md`, `docs/GTM_Whitepaper_Metrics.md`, `docs/publishing-crates.md`, and `README.md`.

Each claim was checked against live state, not just the source tree:

- **Registries:** PyPI JSON API, npm registry, crates.io API, and `gh repo view`, `gh release list` and `gh run list` for GitHub.
- **Onboarding simulation:** a clean Python 3.10 venv with `pip install` of each advertised package, then the README snippets were run. In a clean npm project, `@temporal-hypergraph/sdk` was installed and imported via ESM, CJS and the `/ai` subpath.
- **GPU evidence:** `kaggle_output/thg-vllm-cuda-test.log`, `kaggle_gpu_job/*`, `scripts/run_kaggle_test.sh`.
- **Benchmark provenance:** `results/phase7/*`, `results/f1.csv`, `.github/workflows/*`.

Status legend: **Done** (shipped and verified), **Partial** (shipped with a gap), **Missing** (planned, not shipped), **Deferred** (consciously postponed or pivoted; see section 2).

## 2. Discrepancies & Deferred Items

These are deliberate drops, pivots and deferrals. None of them blocks launch on its own, provided the public narrative keeps describing them accurately, as the current launch post mostly does.

1. **10M-edge ingest (whitepaper target), and 100M-edge scale validation (docs/06).** The 10M run stopped at about 3.0M edges (in-memory mode) and about 3.5M (WAL-buffered) because the 8 GiB M3 started paging, and the harness correctly refused to report swap-bound throughput. Extrapolated need: about 3.1 GiB of heap for 10M edges. 100M edges was never attempted. Both are disclosed in the launch post (section 4) and README. **Follow-up:** rerun `scale_stress` on a machine with 32 GB or more and regenerate the whitepaper.
2. **crates.io namespace collision.** `engine-core` belongs to an unrelated crate. The plan is to publish as `temporal-hypergraph-core` with a `package =` alias, keeping the import name. Nothing is on crates.io yet. The launch post does not mention crates.io, which is correct. **Follow-up:** do the rename and publish all four crates in order before anyone asks "where's the crate?". This also gives users `cargo install grpc-server` (see blocker 3).
3. **npm scope.** The TypeScript SDK ships as `@temporal-hypergraph/sdk`, and the README, launch post, `package.json` and the npm registry agree. npm provenance was dropped because the source repo is private. **Follow-up:** re-add `--provenance` and `id-token: write` once the repo is public. Deprecate or unpublish the `0.0.0-stage` stub.
4. **Headline pivot from "90% less hallucination, 80% lower cost" to measured retrieval metrics.** `GTM.txt` built the ROI pitch on token arbitrage: about 2,000 tokens retrieved instead of 100,000 sent. The benchmark does not support an 80% cost claim. At a matched budget the hypergraph uses 666 tokens against 656, and against vector k=5 it uses 65.5% more. The real win is 7.2x recall per token and 0% stale facts. The launch post states this correctly. **Rule for launch week:** do not reuse the `GTM.txt` 80% and 90% figures in replies, tweets or the HN title.
5. **Baselines changed.** Neo4j became an in-process NetworkX "Neo4j-style" model, and Pinecone became exact FAISS. Both are disclosed, including the caveat that a real Neo4j has a faster traversal core.
6. **GPU target changed from RunPod RTX 4090 / A6000 with Llama-3-8B to a Kaggle T4 with Qwen2.5-1.5B.** The T4 has no bf16, hence FP16. Blocks are 0.44 MiB, not the 8 MB in the spec, so the docs/04 latency targets remain unmeasured.
7. **vLLM integration depth.** `Integration.txt` and docs/04 describe registration through `--kv-transfer-config` and `BlockSpaceManager` hooks. What shipped is the storage tier plus a manually driven offloader. The connector that vLLM itself calls was not built. This becomes a blocker only because of how the launch post and README word it (blocker 4).
8. **Python SDK versions lag.** `hypergraph-client`, `langchain-hypergraph`, `llama-index-hypergraph`, `hypergraph-offloader` and `hypergraph-evaluation` are at 1.0.0, while the native wheel and npm SDK are at 1.0.1. The launch post says "Python and TypeScript SDKs are at v1.0.1".
9. **Performance targets missed but not claimed.** Memory per hyperedge is about 338 B against a target under 128 B, and fsync WAL p99 is 46.86 ms against under 1 ms. The design docs that state these targets are linked from the README, so an attentive reader may notice. **Optional follow-up:** add a "spec vs measured" note to the README Documentation section.
10. **Validation scope smaller than spec.** The SIGKILL harness runs 3 × 100 K in CI, against 100 × 1M in the spec. The 24 h endurance run, Valgrind sweep, LongMemEval, HelloBench, the 30%-noise extraction chaos test and the end-to-end KL-divergence test were not run. None of these are claimed.
11. **Qdrant.** The planning docs name Qdrant as the hybrid vector store. The engine stores embeddings natively, and Qdrant appears only as an evaluation baseline (`benchmarks/`, `competitor_bench.py`). This is consistent with the README.
12. **Commercial tiers and Ollama.** These were roadmap items in `GTM.txt` and were not built. Fine for an OSS launch. Do not imply a hosted service exists; the `api_key="your_key"` snippets could be read that way, which is a minor risk.

## 3. Actionable Launch Blockers

Each item would embarrass us on Hacker News, fail a new user's first five minutes, or contradict a published claim. None of them requires new engine code.

### Blocker 1: The GitHub repository is private

- **Evidence:** `gh repo view` reports `"visibility":"PRIVATE"`, and an anonymous request to `https://github.com/Divyansh151005/Temporal-Hypergraph-Engine` returns HTTP 404. `kaggle_gpu_job/main.py` notes that "the GitHub repo is private".
- **Impact:** every repository link in the launch post 404s for readers, including the source links in sections 2.1 to 2.3 and section 5, the repository link, and the reproduce section. "Everything below is reproducible from the repo" becomes false. The README's build-from-source path, the integration READMEs (`pip install -e integrations/...`), and the only way to get `hypergraph-server` are all unreachable. The PyPI and npm "Homepage" and "Repository" links also 404.
- **Fix:** make the repository public. Then re-enable npm provenance and add repository topics (`rag`, `knowledge-graph`, `rust`, `vllm`, `llm-memory`).

### Blocker 2: The README's Python, LangChain and LlamaIndex quickstarts fail on `pip install`

- **Evidence:** PyPI returns 404 for `hypergraph-client`, `langchain-hypergraph`, `llama-index-hypergraph` and `hypergraph-offloader`. In a clean venv, `from hypergraph_client import TemporalHypergraph` raises `ModuleNotFoundError`. `publish.yml` only publishes `hypergraph-engine-native` and the npm SDK.
- **Impact:** three of the five "add temporal memory in one line" snippets in the README cannot be installed. This is exactly the one-line DX that `GTM.txt` Phase 1 identifies as the adoption gate. The launch post's claim that the "Python … SDKs are at v1.0.1" is also inaccurate: they are at 1.0.0 and unpublished. The unclaimed names are also open to squatting once the post draws traffic.
- **Fix (preferred):** bump the four pure-Python packages to 1.0.1. Add a PyPI Trusted Publisher and a `publish.yml` job for each (`python -m build` plus `pypa/gh-action-pypi-publish`), cut v1.0.2 or publish manually, and update each integration README to `pip install <name>`.
- **Fix (minimum):** if publishing slips, change the README snippets to state "install from source" with the `pip install -e` commands, and change the launch post to "the native Python module and TypeScript SDK are at v1.0.1".

### Blocker 3: Users cannot get a server without cloning and compiling Rust

- **Evidence:** there is no Dockerfile, no prebuilt `hypergraph-server` asset on the GitHub releases, and nothing on crates.io. `hypergraph_client/server.py` tells users to "run `cargo build --release -p grpc-server`".
- **Impact:** the npm SDK (published and working) and the Python, LangChain and LlamaIndex clients all need a running `hypergraph-server`. A TypeScript developer who runs `npm install @temporal-hypergraph/sdk` from the launch post has nothing to connect to until they install a Rust toolchain and compile a release LTO build of a gRPC server. Once blocker 1 is fixed this becomes possible, but it is still a poor first five minutes, and the launch post's "Try it" section omits the server step.
- **Fix (minimum, needed for launch):** add the server step to the launch post's "Try it" section (clone plus `cargo run --release -p grpc-server --bin hypergraph-server -- --data-dir ./data`). Lead with the zero-server path, `pip install hypergraph-engine-native` plus the PyO3 snippet, which already works end to end from PyPI.
- **Fix (strongly recommended):** attach prebuilt `hypergraph-server` binaries (linux-x86_64, linux-aarch64, macOS-arm64) to the release, or publish a Docker image, or complete the crates.io rename so that `cargo install grpc-server` works.

### Blocker 4: The vLLM integration claim goes beyond what the code does

- **Evidence:** the launch post (section 2.3) says the offloader "plugs into vLLM as a secondary tier for PagedAttention blocks". The README says "a secondary KV-cache tier for vLLM PagedAttention", calls `python/hypergraph_offloader` a "vLLM connector", and draws "vLLM PagedAttention via hypergraph_offloader" in the architecture diagram. In the code, there is no vLLM connector or secondary-tier class, and `hypergraph_offloader` does not import vLLM. The Kaggle test runs `vllm.LLM(...).chat()` and the offloader round trip independently, on the same GPU.
- **Impact:** this is the claim an HN commenter who knows vLLM is most likely to test. It contradicts our own "limitations next to the claims" positioning, and it is the one place where the narrative clearly outruns the code.
- **Fix (wording only, no code):** describe it as "a zero-copy KV-block store and Python offloader built for vLLM's secondary tier. Verified bit-exact on a CUDA T4 (GPU to engine to GPU, `torch.equal`). Registering it as a vLLM KV connector is the next milestone." Update the README tagline, the architecture labels and the repository-layout row the same way. Optionally add the Kaggle T4 result to the launch post's section 4 as evidence. It is a credible, honest data point.

### Required before posting (small, but would draw comments)

These are not blockers on their own, but each is a five-minute fix and each is the kind of detail HN readers check.

1. **Commit the benchmark raw data.** `/results/` is gitignored, so `results/phase7/*.json` and `*.csv` (the source of every number in the whitepaper) and `results/f1.csv` are not in the repo. Commit `results/phase7/` (excluding `cache/`), or attach it to the GitHub release and link it from the whitepaper. Otherwise "generated by a script from the benchmark JSON" cannot be audited.
2. **Commit the GPU verification.** `kaggle_gpu_job/`, `scripts/run_kaggle_test.sh` and the `.gitignore` change are untracked or uncommitted. If the T4 run is cited (recommended under blocker 4), commit them.
3. **README PyO3 snippet: `decay_lambda=0.0` does not disable decay.** The snippet runs, but `traverse(["org:microsoft"], k_hops=3, as_of=1700000000)` on a 2014 fact returns `score: 1.37e-36`. Passing `decay_lambda=0.0` explicitly returns the same value. Probing shows a fixed 30-day half-life: the score is 0.977 after 1 day and exactly 0.5 after 30 days, whatever the argument. The signature advertises `decay_lambda = 0.0` as the default, so users will expect 0.0 to mean "no decay". This is either a scoring bug or an undocumented default, and the first person to copy the README snippet will see it. Before launch, either document the behaviour in the `traverse` docstring and the README, or change the snippet's `as_of` so the output looks reasonable. A code fix is out of scope for this audit.
4. **Align SDK version wording.** After blocker 2 is fixed, make sure every Python package actually reports 1.0.1, or reword the launch post.
5. **Whitepaper provenance.** The numbers were captured on `efd737f-dirty`. Either rerun on a clean tagged tree (`v1.0.1`) and regenerate, or add a sentence explaining what was uncommitted at measurement time.
6. **npm stub.** Deprecate `@temporal-hypergraph/sdk@0.0.0-stage`.

### Verified as launch-ready (no action needed)

- `pip install hypergraph-engine-native` works on Python 3.10 to 3.13 for Linux x86_64 and aarch64, macOS x86_64 and arm64, and Windows x64. The README PyO3 snippet inserts and traverses correctly.
- `npm install @temporal-hypergraph/sdk` installs, and ESM, CJS and the `/ai` subpath resolve. The `/ai` subpath correctly needs the optional `ai` peer, which the SDK README documents (`npm install @temporal-hypergraph/sdk ai zod`).
- The launch post's TL;DR, section 3 and the README tables are numerically consistent with `GTM_Whitepaper_Metrics.md`. Spot-checked: 0%, 45.1%, 52.5% and 52.9% stale rates; 62.2% vs 8.6% recall (7.2x); 0.530 vs 4.126 ms (7.8x); 375 ns vs 40.01 ms; 14.8 K vs 998 reads/s; 200 K/s ingest.
- The code excerpts in the launch post (ArcSwap field, SIMD `exp`, WAL recovery fix) match the source files they cite.
- CI is green on the launch commit (Core Engine QA and evaluation), including Miri on `vllm-kv-store` as the post claims, Loom, the WAL corruptor and the SIGKILL harness. The v1.0.1 Publish run succeeded.
- Limitations are disclosed next to the claims: p99 tail, read-path reclamation, publish cost growth, synthetic data, the 10M-edge shortfall, and NetworkX instead of Neo4j.
